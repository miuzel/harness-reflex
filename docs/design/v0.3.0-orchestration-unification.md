# v0.3.0 编排层统一设计：DSH 插件与 Claude 插件共用一份决策

> 定位：**决策文档，不是资料堆**。依据是当前 HEAD `6872581` 的两份实现——
> 共享层 `src/hook/decision.ts`（g-040 抽出的 `HookDecision`，下称 **HOOK**）、
> DSH 侧引擎 `packages/dsh-harness-reflex/src/interventions.ts`（下称 **DSH**，行号以 `6872581` 为准）。
> 边界：只写设计与范围，**不改任何实现代码与测试**；所有「文件:行号」都在本基线用 `read`/`grep` 核对过。
>
> 状态：**待负责人拍板**（§7 共 5 件事）；快照 2026-11-02；设计基线 `0.3.0-harnesses` 的 `6872581`。

## 0. 结论速览

- **一个真实缺口**：DSH 与 Claude 侧共享 `core/`（`suspicionOf`/`applyPruneFloor`/`claimCandidates`/
  `assembleEvidence`/`evidenceOf`），**不**共享「拿什么去问、花什么预算去问、问完怎么记账、记账怎么措辞」。
  这四件事在两侧各写了一遍（HOOK §2.1 表）。
- **改造不是搬代码，是接缝**：七个差异里有五个是「宿主能力」，只有两个（会话粒度、判定窗口）是
  「状态载体选错了」。因此**不把 DSH 塞进 `HookDecision`**（那会逼 HOOK 长出宿主编排，Claude 侧白白变复杂），
  而是把两侧共同的那一层抽到 `core/` + 新增 `ports/host.ts`，让 `HookDecision` 成为它的第一个宿主、
  DSH 引擎成为第二个。
- **最小可行第一批 = 剪枝**（§5.3）：它的执行顺序本身就是安全属性（保留原文 → 判定 → 组合 → 比对缩小 →
  才记节省），是四批里唯一「顺序错了会摧毁数据」的一批；先把它做成共享层，剩下三批的接缝形状就被逼出来了。
- **行为对照可执行**（§6）：三层——① 决策序列对拍（同一输入序列 → 规范化 ledger/审计记录逐项相等）；
  ② 全量信号对拍（把 DSH 的 `InterventionReport` 与 `readEvents(limit)` 快照压进同一基线）；
  ③ 随机序列差分（固定种子生成输入，两侧引擎跑同一序列）。判据是 §6.3 的 12 条断言。

## 1. 归属拆分（问题一）

### 1.1 总表

| 编排项 | 归共享层 | 归宿主端口 | 依据 |
|---|---|---|---|
| **判定顺序**（先判什么） | ✅ 触发条件、预算门、锁存、模式分流 | ❌ 只在「顺序的接缝」处回调（下游已决策的判断、观测摄入） | DSH 把下游判断放在**最前**（`interventions.ts:897`）、HOOK 放在最后；顺序差异里只有「何时看下游」是宿主的 |
| **预算扣减** | ✅ 三类计数器的**语义与顺序**（动作 / 判定 / 每轮收尾上限） | ❌ 计数器的**存放与原子性**（锁 / 内存） | HOOK 的 `#reserve`/`#reserveClosing` 把「检查 + 自增」写成一个锁内读改写（`decision.ts:329-377`）；DSH 的 `actionWithinBudget`+`bookAction` 是两步（`core/policy.ts:113-127`），但 DSH 是单线程进程内，两步之间没有 await，语义上等价 |
| **账本字段** | ✅ 「一条决策的最小可审计事实」：能力 / 动作 / 模式 / applied / skipReason / 计数 / 判定成本 / 轮次 | ❌ 存储形态与**宿主专属字段**（`agentId`、`originalLocator`、`transcriptPath`…） | HOOK 写 `HookLedgerRecord`（`state/file-store.ts:92-113`）；DSH 写 `InterventionAuditRecord`（`session-audit.ts:96`）。两者重叠 9 个字段、各自独有 8–20 个字段 |
| **反馈文案模板** | ✅ 模板骨架（何处插变量、截断上限、空事件措辞） | ❌ 语言与语气（两侧现有文案不同、用户不同） | 现存两份：HOOK 英文陈述式（`decision.ts:620-625`、`823-827`、`983-987`、`1010-1013`）；DSH 英文但带 `Reflex intervention:` 前缀与置信度（`interventions.ts:2308-2348`） |

### 1.2 判定顺序：逐项

「判定顺序」要被共享，必须先把每个判断拆成**与宿主无关的三类**。

| 类别 | 归属 | 内容 | HOOK 侧证据 | DSH 侧证据 |
|---|---|---|---|---|
| T 触发 | 共享 | 本事件是否值得判（重复 / 连续失败 / 振荡 / 跨行大 payload / 有完成声明） | `suspicionOf`（`decision.ts:546-551`）、阈值检查（`674-676`）、`claimCandidates`（`887`） | `suspicionOf`（`interventions.ts:929-934`、`1155-1160`、`1774-1779`）、阈值检查（`1425-1441`）、`claimCandidates`（`1233`） |
| G 门 | 共享 | 模式 off / 预算 / 会话冲突 / 已锁存 | `510-522`、`569-578`、`677-678`、`804-812`、`906-915` | `899`、`946-954`、`1129-1151`、`1449-1457`、`1472-1478`、`1780-1789`、`1235-1262` |
| H 宿主事实 | 端口 | **下游已给出的决策**、**本插件自家工具的排除**、**信号是否已中止**、**结果的有效内容** | HOOK 无此项（命令钩子没有瀑布流） | `897`（先 `next()`）、`900`/`1038`（ownTools）、`901`/`1127`/`1243`（signal）、`1054-1056`（取 `downstream.content`） |

**结论**：判定顺序 `T → G → 买判定 → 按模式执行或跳过 → 记账` 归共享；唯一真正属于宿主的是
**「H（下游事实）在顺序里的位置」**——DSH 必须在 T 之前拿到 `downstream`（它要决定 `applied` 是否成立，
`interventions.ts:998-1001`），而 HOOK 的 `downstream` 恒为空。这一条用一个回调表达：
`host.peekDownstream(): DownstreamFacts`，HOOK 实现返回 `{kind:'allow', content:undefined}`，
DSH 实现返回真实瀑布结果。顺序本身（谁先谁后）留在共享层。

### 1.3 预算扣减

| 预算 | 共享层负责 | 端口负责 | 一致性风险 |
|---|---|---|---|
| 每轮动作数 `maxInterventionsPerTurn` | 检查时机、扣减时机（**只有真的要执行时才扣**） | `updateState(mutate)` 的原子性 | DSH 在 observe 模式下也 `bookAction`（`interventions.ts:1004-1007`、`1190-1195`、`1604-1605`），理由写在注释里：observe 必须「像 active 一样消费同一个 episode」；HOOK 没有 observe 扣减的等价物，**这是要显式保留的语义差异，不是 bug** |
| 每轮判定数 `maxJudgmentsPerTurn` | 同上 | 同上 | 两侧都把「分类 + 核验」算成一次判定（DSH `1257`；HOOK `906`），但 DSH 的 `runJudgment` 内部还会再检查一次（`core/judge.ts:313-316`），HOOK 只有一次（`decision.ts:345-346`）。合并后必须只保留一处 |
| 每会话判定数 `maxJudgmentsPerSession` | 同上 | 会话生命周期（何时清零） | HOOK 的会话预算**永不清零**（`decision.ts:844-851` 只重置 turn 与 turn 级预算）；DSH 同样只在 `#state` 首次创建时为零（`interventions.ts:2078`） |
| 每轮收尾上限 `maxClosingBlocksPerTurn` | `#reserveClosing` 的检查 + 扣减 | `continues.closing` 存放 | 只存在于 HOOK（`decision.ts:363-377`）；DSH 侧等价物是 `applied.has('closing:turn:N')` 锁存（`interventions.ts:1235`、`1343-1344`）。**两者语义不同**：HOOK 限次，DSH 限一次 |

### 1.5 反馈文案模板

两侧文案**都**是「前缀 + 计数 + System One 结论 + 建议」，只有措辞不同：

| 能力 | HOOK 文案 | DSH 文案 | 共享的部分 | 宿主的部分 |
|---|---|---|---|---|
| 停滞拒绝 | `harness-reflex: this call repeats a pattern …`（`decision.ts:620-625`） | `Reflex intervention: <tool> was called with identical arguments N times …`（`interventions.ts:2308-2316`） | 变量清单：工具名、重复次数、模式、置信度、建议文本、截断上限 | 前缀、人称、是否报置信度、是否报「调用未执行」 |
| 纠偏上下文 | `harness-reflex: N consecutive tool calls failed …`（`decision.ts:823-827`） | `Reflex intervention: <tool> failed N consecutive times with <err> …`（`interventions.ts:2330-2338`） | 同上 + 错误摘要 | 同上 |
| 收尾异议 | `harness-reflex: this turn claims completion but its own tool evidence contradicts it: …`（`decision.ts:983-987`） | `Reflex closing check: this turn is about to close …`（`interventions.ts:2341-2348`） | 反证清单、截断上限（HOOK 900 / DSH 600） | 同上 |
| 剪枝说明 | **无**（不发模型可见文本，`decision.ts:735` 只换 `updatedToolOutput`） | 有，但**只进审计**（`interventions.ts:2206-2250`、`1902-1906` 注释） | 模板骨架（`2206-2250` 已是结构化数据驱动） | DSH 独有；HOOK 不需要 |

**结论**：共享层只产出 `FeedbackVars`（结构体）与 `templateId`；渲染函数留在各宿主。
理由：文案是**用户可见的产品决策**，跨产品共享会让任一侧改文案都要动共享层，而且两侧的
「谁给谁看」不同（HOOK 的 deny 给模型看，DSH 的剪枝说明只给人看）。截断上限
（`FEEDBACK_CHARS = 600`，`interventions.ts:165`）归共享层作为默认值。

**依赖方向**：`core/* ← ports/host.ts ← 宿主装配`。`core/` 仍不得 import `node:fs`、不得 import 任何适配层
（沿用 `v0.2.0-harness-plugins.md` §2.1 的规则 1）。`ports/host.ts` 只放类型与接口，零实现。

**为什么不用 `HookDecision` 直接当共享层**（被否方案）：

| 方案 | 否决理由 |
|---|---|
| A. DSH 直接 `new HookDecision({store: MemoryStateStore})` 并改 `handle` 的分支 | `handle` 是 `switch(event, 7 个 HookEvent)`（`decision.ts:485-504`），DSH 的四入口（`toolCall`/`toolResult`/`preStep`/`turnStopping`）没有一一对应；强行套用必须在 HOOK 里长出台词（ownTools、下游 peek、steer），Claude 侧背上无用的宿主编排，且 `CLAUDE_PLUGIN_OPTION_*` 兼容面受影响 |
| B. 把 DSH 的状态迁到 `HookStorePort` 并保留 `AgentState` 双写 | 两套状态必然漂移；且 `HookStorePort` 的 16 个方法（`store-port.ts:27-83`）里有 6 个只服务命令钩子的「每次一个进程 + 重投递」（`writeDecision`/`readDecision`/`claimDecision`/`releaseDecisionClaim`/`eventsHaveKey`/`ledgerHasKey`），DSH 是进程内单次执行，用不到这些幂等原语 |
| C. 先用一份「行为快照」把 DSH 冻住，再整个重写 | 风险不可控（`interventions.ts` 2580 行、4 个入口、92 条测试）；且没有中间可回滚点。本文的 §5 分批方案是它的逐步版 |

**被采纳方案**：抽共享层（新），两侧各留一个**薄适配层**。适配层的目标体量：
HOOK 侧从 ~350 行（五个 handler + 两个 reserve）降到 ~120 行；DSH 侧从 4 个入口共 ~900 行降到 ~450 行
（估算，按 §5 的逐批统计校准）。

## 3. 七个差异的逐一方案（问题二）

### 3.1 状态载体：`AgentState` ↔ `HookStorePort`

| 项 | DSH 侧（`AgentState`） | 共享层需要的 | 方案 |
|---|---|---|---|
| 轮 / 步 | `turn`、`step`（`interventions.ts:2084-2085`，由 `preStep` 维护 `1106-1123`） | 事件归属 | 保留在 DSH 状态里；共享层只接收 `turn/step` 作为 `ObservedStep` 的字段 |
| 三个预算计数 | `interventions`、`judgmentsTurn`、`judgmentsCount`、`judgmentsSession`（`interventions.ts:2075-2078`；`judgmentsTurn` 实为「归属轮次」，`1109-1111` 只在换轮时写） | §1.3 | DSH 用 `MemoryStateStore` 的 `budgets`（`memory-store.ts:41`）；DSH 现有的「每轮清零由 `preStep` 驱动」（`1106-1122`）改成 `resetTurn()` 端口方法 |
| 观测窗口 | `steps: ObservedStep[]`（`interventions.ts:2086`，上限 12，`147`） | 判定历史 | DSH 直接传数组（零拷贝）；HOOK 由 `readEvents(30/40)` 回读（`decision.ts:771-783`、`1031-1037`） |
| 判定缓存 | `verdictTurn`/`verdictKey`/`verdict`（`interventions.ts:2079-2081`） | 摘要 | `runJudgment` 已把这两件事编码成键（`core/judge.ts:257-262`、`300-301`），把「键」提到共享层即可 |
| 锁存集合 | `waited`/`applied`/`denied`/`refused`（`interventions.ts:2081-2084`） | 摘要 | 四个集合语义**都归共享层**（它们是「这一轮不许重复干预」的规则，不是存储）。但**只有 DSH 用全四个**：`waited`（等待已判）、`refused`（被拒调用的结果不再判定，`1043-1049`）在 HOOK 侧没有对应物；HOOK 只用 `applied`（`pre` 事件的签名）与 `denied` 的等价物 `SessionState.appliedSignatures`（`file-store.ts:64`） |
| 剪枝 memo | `#memo`（`interventions.ts:711`，按 `sessionKey:digest`，键见 `2253-2258`） | 摘要 | 归共享层（「同一 payload 不重复付判定」是规则）；键与 DSH 的 `sessionKeyOf`（`2552-2555`）一致 |
| claims / evidence | `claims`、`evidence`、`evidenceSuspect`（`interventions.ts:2072-2074`） | 收尾核验输入 | 归共享层（`core/evidence.ts` 已有 `evidenceOf`/`assembleEvidence`） |
| 周期维护 | `MAX_AGENTS=64`（`interventions.ts:159`）、`MAX_MEMO=128`（`161`）、`MAX_STEPS=12`（`147`） | 上界 | 端口方法 `evict()`；默认值放共享层配置 |
| 留存 | `#retain` 回调 → Session log（`interventions.ts:706`、`1442-1448`、`1621-1648`） | 原文留存 | 抽象为 `RetentionPort.persist(key, text): Locator \| undefined`；**`MemoryStateStore.retainOriginal`**（`memory-store.ts:183`）可作 DSH 的默认实现，DSH 现行 Session log 实现保留为第一实现（保留原文可被 `readPrunedOriginal` 读回，`session-audit.ts:546`） |

**关键判断**：`AgentState` 不是要「换成 `HookStorePort`」，而是**拆成「规则」与「存储」两半**——
规则（锁存、memo、窗口上限、预算语义）进共享层，存储（每 agent 一份、进程内生命周期）留在 DSH。
`HookStorePort` 是 Claude 侧的存储实现，不是共享层的接口；共享层只认 `HostOrchestrationPort`。

**风险**：`MAX_STEPS=12`（DSH）与 `readEvents(limit=30/40)`（HOOK，`decision.ts:772`、`1031`）是两个不同的窗口。
共享层如果取其一，会改变另一侧的行为。保守建议：**窗口大小由端口配置**，默认沿用各自现值，不进共享默认值。

### 3.2 会话粒度：`agent + native session` ↔ 单 `sessionId`

| 事实 | DSH | HOOK | 方案 |
|---|---|---|---|
| 主键 | `agentKeyOf(agent)`（`interventions.ts:2522-2528`），fallback `'anonymous'` | `sessionId`（`decision.ts:264`、`491`） | 共享层的输入是 `SessionScope { sessionId, agentId? }`；`agentId` 可选 |
| 隔离单位 | **每个 agent 一份** `AgentState`（`interventions.ts:690-710` 类注释「isolation is structural」） | 每 session 一份 | 保留：DSH 的 `agentId` 事实上必填，但 `agentKeyOf` 的 `'anonymous'` 兜底（`2527`）是个隐患——两个没有 `id` 的 agent 会共用一个状态槽。**这是行为变更**，是否顺手修见 §7-2 |
| memo 归属 | `sessionKey`（优先 `session.id`，fallback `agent:<agentId>`，`2552-2555`） | digest 存在 per-session store | 保留：共享层以 `SessionScope` 作 memo 命名空间，不猜 |
| 轮边界 | `agent/pre-step` 的 `payload.turn` 变化（`1106-1122`） | `stop` 事件自增（`decision.ts:842-851`） | **差异必须保留**：DSH 的轮边界是**开始**，HOOK 是**结束**。共享层的 `turn` 由端口提供，不自增 |

**为什么不能简单统一成 `sessionId`**：DSH 一个 session 里可以并发多个 agent，共享一个 session 状态会让
A agent 的干预预算/锁存串到 B agent。反过来让 HOOK 用 `agentId` 没有意义（命令钩子里只有一个 agent）。
**结论**：共享层接受的键是 `SessionScope`，DSH 传 `{sessionId: sessionKeyOf(agent), agentId}`，
HOOK 传 `{sessionId}`。共享层**不**做「按 agent 拆分」的判断——那是 DSH 适配层的职责。

**风险**：`sessionKeyOf` 的 fallback 是 `` `agent:${agentKeyOf(value)}` ``（`2554`），而 `agentKeyOf` 的
fallback 是 `'anonymous'`。三层 fallback 叠加后，两个没有 `session` 也没有 `id` 的 agent 会共享
memo 与预算。**保守建议**：第一批不改（会动测试），在 §7-2 显式提出。

### 3.3 判定窗口：`agent/pre-step` 实时维护 ↔ `readEvents` 回读

| 项 | DSH | HOOK | 方案 |
|---|---|---|---|
| 窗口来源 | 内存数组 `state.steps`（`interventions.ts:2086`），每次 `toolResult` 追加（`1058-1068`、`2116-2119`） | `readEvents(sessionId, 30/40)`（`decision.ts:771-783`、`1031-1037`） | 共享层接收 `ObservedStep[]`，来源由端口决定 |
| pre-execute 的「本次调用」 | 本地构造 `pending`，**不提交**历史（`interventions.ts:909-913`、`2101-2113`） | Hook 侧没有「调用前」窗口，`pre` 事件由 `#finish` 提交（`decision.ts:552-558`） | 共享层支持 `window: [...history, candidate]`，`candidate` 由 `host.observe({phase:'pre'})` 构造 |
| 等待剔除 | `progressSteps` 过滤 `step.wait === true`（`interventions.ts:476-478`、`919`、`1154`） | 无 | 归共享层（随 §3.4 一起上移），默认值是「有 wait 步骤就剔除」（`477`） |
| 证据回读 | `state.evidence` 累积（`interventions.ts:1077`、`2134-2149`） | 从 `events` 过滤 `kind in {post, failure}`（`decision.ts:1031-1037`） | 保留两种：共享层接收 `EvidenceEntry[]`，DSH 传内存，HOOK 传回读结果 |

**结论**：判定窗口的**语义**（哪些步骤算数、窗口多大、等待是否剔除）归共享；
**来源**（内存 / 回读）归端口。这是七个差异里唯一「只差实现方式」的一条，也是改造中最安全的一条。

**风险**：HOOK 的 `readEvents` 返回**最新在前**（`store-port.ts:37` 注释「newest first」），而 `suspicionOf`
期望**最旧在前**（`core/judge.ts:111` 从尾部切片）。共享层必须明确定义顺序并在 adapter 里做一次反转，
现有 `decision.ts:774-783` 的 `prior.map` 与 `1031-1037` 都**没有**反转，即已经依赖 store 返回的顺序。
**保守建议**：共享层入口一律要求「oldest first」，由 adapter 负责与 store 的约定对齐，并加一条顺序断言（§6.3 第 A10 条）。
**注意**：这一条如果判断错了（比如 `FileStateStore.readTail` 其实返回最旧在前），就是一次**静默的行为变更**
——所以 A10 断言必须**先**在 legacy 上跑通、再拿它守 shared，不能凭注释。

### 3.4 合法等待豁免：`isWaitQuery`/`pollShapeOf`（`job_kill` 边界）

| 事实 | 依据 | 方案 |
|---|---|---|

| 非白名单工具可用 `pollShapeOf` 成为「等待嫌疑」 | `404-413`（`POLL_HANDLE_FIELD`，`392`） | 迁入 `core/wait.ts`；**但注意**：`interventions.ts:920` 的 `pollShapeOf` 分支**没有测试覆盖**（`interventions.test.ts:3354-3357` 只测了函数本身，没有测引擎走这条分支的行为）。保守建议：上移时**一并补行为测试**（属于新增测试，不在本轮范围） |
| 等待步骤不计入重复/失败/振荡 | `progressSteps`（`476-478`） | 迁入 `core/wait.ts` |

| 已判定的等待不再复问 | `state.waited.has(signature)`（`interventions.ts:924-927`） | 归共享层锁存 |

**`job_kill` 边界的结论**（这是问题二里被点名的三条之一）：

1. **语义**：`job_kill` 是终止动作，不是重复查询；一个反复 `job_kill` 的 run 不是在等待，而是在循环。
   所以它**不豁免**，走普通重复判定（第 3 次被拦）。
2. **实现**：`WAIT_QUERY_TOOLS` 只有两项（`345-348`）；`pollShapeOf` 的启发式也**不会**把它算作等待嫌疑——
   它的参数是 `{job_id: 'job-7'}`，`POLL_HANDLE_FIELD`（`392`）匹配 `job_id`，所以 `pollShapeOf('job_kill')`
   **会**返回 `'poll-handle'`。这意味着 `job_kill` 第 3 次重复时会被当作「等待嫌疑」去问 System One
   （`interventions.ts:935-945`），而不是被当作普通重复**直接**拦。
   **这不是 bug**，是「让判定者决定」：`935-944` 的注释写明「the tool list only decides that this repetition
   is worth asking about」。但它必须作为**行为契约**保留，不能在上移时被简化掉。
3. **断言**（质量判据 4）：迁移后必须有三条——`isWaitQuery(job_kill)` 为假、`job_kill` 第三次重复仍会买判定、
   `waitGoalOf` 对 `job_kill` 给出的 `suspect` 字段是 `poll-handle`（而非 `wait-query`）。

**风险**：`WAIT_QUERY_TOOLS` 是**宿主工具名**（DSH Host 的 `@deepseek-ai/dsh-tool-jobs`），不是 harness 无关的。
放进 `core/` 意味着 Claude 侧也会带上 DSH 的工具名——虽然 Claude 侧永不触发（没有 `job_*` 工具），
但这是**概念污染**。保守建议：放进 `core/wait.ts` 但**保持导出**，并在文件头注明「DSH Host 的工具身份表，
其他宿主不注册同名工具即自然不触发」；比新建 `hosts/dsh/` 更小的改动面。

### 3.5 权限单调：`tools/pre-execute` 只在下游 allow 时追加 deny

| 事实 | DSH | HOOK |
|---|---|---|
| 先问下游 | ✅ `const downstream = await next()`（`interventions.ts:897`） | ❌ 无下游（`decision.ts:510` 起直接判） |
| 只在下游是 `allow` 时追加 deny | ✅ `downstream.kind === 'allow'`（`interventions.ts:998`） | ❌ 直接返回 `preToolUseDeny`（`decision.ts:627`） |
| 下游已 deny/ask/block 时原样传递 | ✅ `999-1001`（记 `downstream-decided`）、`1010-1019`（fail-open） | ❌ 不适用 |
| 结局单调性 | ✅ 只会把 allow 变成 deny，绝不把 deny 放宽成 allow（`880-895` 注释） | ❌ 不适用（无瀑布流） |

（表中「HOOK」列写作 ❌ 是**如实记录**：命令钩子没有瀑布流，因此「权限单调」在 Claude 侧不是一个可比的语义，
而不是「缺失的能力」。）

**方案**：`peekDownstream` 是 `HostOrchestrationPort` 的**可选**方法。

```ts
interface DownstreamFacts {
  /** The waterfall's decision when the host has one; `'unknown'` for a host without a waterfall. */
  kind: 'allow' | 'deny' | 'ask' | 'block' | 'unknown';
  /** Whether the host lets this decision add a denial on top. */
  mayRefine: boolean;
}
```

共享层的规则写成一条：**`deny` 只在 `mayRefine === true` 时产出；否则产 `skipReason: 'downstream-decided'`
并保持 `applied: false`。** DSH adapter 返回真实下游，HOOK adapter 返回 `{kind:'unknown', mayRefine:true}`
（命令钩子自己就是权威，等价于现有行为）。

**这不是可选优化，是安全属性**：如果顺序反了（先 deny 再调 `next()`），一个下游已经 `ask` 的调用会被
我们的 deny 覆盖，或者更糟——因为我们把 `next()` 的 deny 结果丢掉，调用会**继续执行**。
所以 §6.3 里给它单独一条断言（A6：下游 `deny` 时我们的返回对象**按对象身份相等**，
即 `assert.strictEqual(result, downstream)`，与 `interventions.ts:897-901` 的现行语义一致）。

### 3.6 `agent/turn-stopping` 的 steer 动作

| 事实 | DSH | HOOK |
|---|---|---|
| 判定 | 收尾证据 vs 完成声明（`interventions.ts:1220-1345`） | 同（`decision.ts:840-1001`） |
| 动作 | `agent.steer(message)`（`interventions.ts:1346`、`2301-2305`），**能失败**（agent 没有 `steer` 时静默） | `{decision:'block', reason}`（`decision.ts:989` → `contract.ts` 的 `stopBlock`）、`stop_hook_active` 短路（`877-886`） |
| 轮次上限 | `maxClosingBlocksPerTurn` **不存在**；用 `applied.has('closing:turn:N')` 限定一次（`interventions.ts:1235`、`1343-1344`） | `#reserveClosing`（`decision.ts:363-377`），默认 2 次（`decision.ts:87`） |
| 消息形状 | `UserMessage`，`source.kind = 'plugin:dsh-reflex'`（`interventions.ts:135`、`2289-2298`） | 纯文本 `reason` |

**方案（判定归共享、动作归宿主）**：

1. 共享层产出 `ClosingVerdict { contradicted: string[]; undecided: number; passed: boolean }` 与
   `AuditableDecision`（含预算扣减结果 `skipReason`）。
2. 共享层的**唯一动作字段**是 `action: 'object-turn-close'`（与 `'deny-call'` 同级），**不含**执行代码。
3. 宿主实现 `applyClosingObject(verdict, vars): void`：
   - DSH：`agent.steer(this.#message(...))`，保留 `plugin:dsh-reflex` 来源与 `boundContextSummary`（`interventions.ts:2291`）；
   - HOOK：返回 `stopBlock(render(...))`。
4. `maxClosingBlocksPerTurn` 是共享层的**配置**（默认 2），但 DSH 设 `1`——与现行的「一次」语义对齐。
   **这是行为变更的边界**：DSH 现值是「一次」，HOOK 是「两次」，共享层必须允许两侧不同，否则必有一侧行为改变。
   保守建议：DSH 显式传 `1`，并在 §6 的对拍里固定这个值。

**为什么 steer 不能上移**：`#message` 依赖 DSH 的 `MessageId`、`boundContextSummary`、`MessageSourceMap`
（`interventions.ts:2289-2298`、`141-146`），这些是 DSH 的会话格式契约（v4，`135-139` 注释），Claude 侧没有。
把它上移会把 DSH 的会话格式引入 `core/`，违反 §2 的依赖规则。

**风险**：`turnStopping` 只是「提议」，真正是否续轮由 DSH 的 loop 决定（`interventions.ts:1209-1216` 注释）。
共享层出的 `AuditableDecision.applied` 对 DSH 来说意味着「steer 被调用」，不意味着「回合被延长」。
这一条要写进共享层文档，否则将来有人会以为 `applied` 表示回合真的没关。

### 3.7 `agent/assistant-stream` 观测

| 事实 | DSH | HOOK |

## 5. 分批改造计划（问题三）

四批的顺序是**由「顺序本身是安全属性」的程度倒排的**，不是按行数：

| 批 | 能力 | 顺序敏感性 | 理由 |
|---|---|---|---|
| **P1** | 剪枝 | **最高** | 保留原文 → 判定 → 组合 → 比对缩小 → 才记节省（`interventions.ts:1379-1387` 注释「the order of operations here *is* the safety property」）。顺序错了会**摧毁数据**或**谎报节省** |
| **P2** | 停滞 | 高 | 前置 deny 需要「下游已决策」这一环（§3.5），是四批里唯一改变控制流的 |
| **P3** | 纠偏 | 中 | 只改结果内容（`interventions.ts:1822-1828`），不阻断 |
| **P4** | 收尾 | 中 | 动作靠 steer/block 分歧（§3.6）；`maxClosingBlocksPerTurn` 两侧不同值 |

## 6. 行为对照方案（问题四）

目标是可执行的「同一输入序列 → 相同决策序列」。分三层，缺一层都只能证明「没崩」，不能证明「没变」。

### 6.1 对照对象：什么算「同一个决策」

| 字段 | 算不算「决策序列」的一部分 | 为什么 |
|---|---|---|
| `applied` | ✅ | 判据 3 明确要求 |
| `skipReason` / `skip` | ✅ | 判据 3 明确要求 |
| 预算消耗（`budgets.interventions/judgmentsTurn/judgmentsSession` 前后差） | ✅ | 判据 3 明确要求 |
| 动作种类（`deny-call` / `prune-result` / `corrective-feedback` / `corrective-context` / `steer-closing`） | ✅ | 决定模型可见面的形状 |
| 模型可见文本（`feedback` / `updatedToolOutput` / `additionalContext` / `reason`） | ✅（按字节） | 任何一字的差异都是产品回归 |
| 剪枝副产物（`originalTokens`、`candidateTokens`、`actualSavedTokens`、`floored`、`floorMissed`、`markerOmitted`、`digest`） | ✅ | 谎报节省是安全属性 |
| `at`、`localLatencyMs`、`remoteLatencyMs` | ❌（置零或剔除） | 时钟与调度噪声 |
| `id`（`hr_...`） | ❌（剔除） | 随机后缀 |
| `agentId`、`originalLocator`、`turn`、`step` | ✅（保留但归一化） | 归一化：`turn/step` 照原样，`originalLocator` 只比较**存在性**与 digest 后缀 |

### 6.2 三种对拍方法，组合使用

**方法 A：决策序列对拍（主方法，每批必跑）**

构造同一组输入序列，分别喂给旧引擎（legacy）与新引擎（shared），把两侧的审计输出规范化后 `deepEqual`。
输入序列用一个**共享的 script 结构**描述（不依赖任何一侧的接口）：

```ts
type Step =
  | { ev: 'tool'; tool: string; args: unknown; result: string; isError?: boolean; downstream?: 'allow' | 'deny' | 'ask' | 'block'; failDownstream?: boolean }
  | { ev: 'pre-step'; turn: number; step: number; downstream?: 'enter' | 'abort' }
  | { ev: 'assistant'; delta: string }
  | { ev: 'turn-stopping'; turn: number; stopHookActive?: boolean };
```

两侧各写一个 ~80 行的 `replay()`：DSH 侧把 `tool` 翻译成 `{toolCall, toolResult}`，把 `pre-step` 翻译成
`preStep`，把 `turn-stopping` 翻译成 `turnStopping`；新引擎（shared 模式）走同一组公开入口。
HOOK 侧不进这条流水线（见方法 B）。

**方法 B：跨宿主信号对拍（用现有 parity 模式扩展）**

现有 `src/hook/parity.test.ts` 已经把「同一事件序列过 `FileStateStore` 与 `MemoryStateStore` 必须逐字节相等」
做成了测试（`src/hook/parity.test.ts:93-104`），它比较的是 `outputs` 与 `ledger` 的「意义」
（`readLedgerMeaning`，`parity.test.ts:80-87`）——**这套 `replay()` + 规范化 `deepEqual` 的骨架可直接复用**。
把同一个思路扩展一份**跨引擎**版本：
让 DSH 的 `toolCall/toolResult` 与 HOOK 的 `handle('pretooluse'|'posttooluse')` 吃同一条 script 的对应切片，
比较「规范化后的 `AuditableDecision`」（§1.4 前六行）。这条**不能**要求 100% 相等：
七项差异（`ownTools`、`deny` 强度、`maxClosingBlocksPerTurn`、轮边界……）注定不同，比较的是**同一能力同一触发**下的
`applied`/`skipReason`/预算三列，其余列以 §6.4 的「已知差异清单」形式显式排除，排除清单本身进测试（每条一个 `it()`，
理由写死）。

**方法 C：随机序列差分（防风化，每批收尾跑一次）**

固定种子（`mulberry32(seed)`，自己写 6 行，不引依赖）生成 200 条随机 script：

| 生成维度 | 取值 |
|---|---|
| 工具名 | `['bash', 'job_output', 'job_list', 'job_kill', 'reflex_choice', 'read']` |
| 参数 | 随机 0–2 个键，键从 `['command', 'job_id', 'run_id', 'path']` 取，值随机 |
| 结果 | 4 类：短、长且多行（可剪）、失败（`isError`）、恰好 100_000 字符边界 |
| 下游 | `['allow', 'deny', 'ask', 'block', 'throw']` |
| 轮边界 | 随机 3–20 步一换 |

同一条 script 跑 legacy 与 shared，`deepEqual` 规范化的决策序列。失败时把 seed 写进断言消息，
可单条复现（`DRIFT_SEED=1234 npm test`）。

### 6.4 已知差异清单（跨宿主对拍时显式排除，每条一个理由）

| # | 差异 | 排除理由 | 风险 |
